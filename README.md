## 起動方法

Node.js 24 と pnpm 12 を使います。Node.js のバージョンは `.node-version`、pnpm のバージョンは `package.json` の `packageManager` で固定しています。pnpm が入っていなければ、`packageManager` に書かれた版を `npm install -g pnpm@<版>` で入れてください。pnpm 10 以降なら、`packageManager` の版が変わったときに自動で切り替わります。

```bash
pnpm install
pnpm dev
# → http://localhost:5173 を開く
```

Cloudflare Vite プラグインを使い、Workers の実行環境（workerd）で動かします。`pnpm build && pnpm preview` で、セキュリティヘッダーを含む本番ビルドをローカルで確認できます。

地図は同じオリジンのタイル・フォント・アイコン画像で描画します。ローカルで地図を確認するときは、下の「地図タイルを作る・保管する」の手順でPMTilesを用意してください。住所検索だけは国土地理院のAPIを使います。

## デプロイ

Cloudflare Workers Static Assets の workers.dev に公開します。リポジトリへの書き込み権限を持つ人が同じリポジトリ内のブランチから作った PR では、チェックと E2E が通ると PR ごとのプレビュー URL を作ります。フォークや Bot が作成した PR ではプレビューを作りません。

Worker は `/map/tiles/<build>/<z>/<x>/<y>.mvt` を地図専用 R2 バケット `find-daycare-map` の PMTiles から配信します。それ以外は静的アセットに渡します。ビルドはアセットを `dist/client`、Worker を `dist/find_daycare` に出力します。CI の E2E とデプロイは、どちらも `wrangler.jsonc` の Worker ソースを使います。

プレビュー URL は `https://pr-<PR番号>-find-daycare.<workers.dev サブドメイン>.workers.dev` です。各実行の GitHub Actions Summary から開けます。GitHub の preview 環境では、最新のプレビューだけがアクティブなデプロイとして表示されます。

`main` にマージすると、CI でビルドし、E2E を通過した同じ artifact を本番にデプロイします。GitHub リポジトリの secrets に `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` を設定してください。

意図的なロールバックには `wrangler rollback` またはダッシュボードを使い、過去の workflow run は再実行しません。

初回の Worker 作成には `wrangler deploy` が必要です。プレビューを使う前に、`main` の本番デプロイを一度成功させるか、認証情報を設定した環境で次を実行してください。Worker が存在するまでは `wrangler versions upload` は使えません。

```bash
pnpm build
pnpm exec wrangler deploy --config wrangler.jsonc --assets dist/client
```

## 開発時のチェック

```bash
pnpm check      # 整形の確認・lint・型チェック・単体テスト・ビルド（CI と同じ内容）
pnpm test       # 単体テスト（Vitest）
pnpm test:e2e   # 本番ビルドに対するスモークテスト（Playwright。初回は pnpm exec playwright install --only-shell chromium）
pnpm format     # oxfmt で整形
```

`pnpm install` を実行すると、lefthook が Git フックを入れます。コミット時は、ステージしたファイルだけを oxlint（自動修正つき）と oxfmt にかけ、直したファイルをステージし直します。プッシュ時は型チェックと単体テストを実行します。

## できること

- **カード一覧**：施設ごとに 0〜5歳クラスの空き人数（緑＝空きあり／×＝空きなし／斜線＝受入れ対象外）、区、定員、開園時間、住所・電話、運営法人、特別保育（延長保育など）、公式サイト・市の資料PDFへのリンク
- **地図**：全施設をピン表示（ピンの数字＝選択中の年齢クラスの空き人数。認可外は角丸の四角いピン）。カードをクリックすると地図がその施設へ移動し、ピンをクリックすると該当カードへスクロール
- **自宅から近い順**：住所（例：「中之島1-3」「阿倍野区文の里1丁目」「浪速区敷津東1丁目」）または「現在地」を指定すると、直線距離・徒歩目安（80m/分）付きで近い順に並び、地図に自宅と選択施設を結ぶ線を表示。町名だけの入力は対象の各区の名前を付けて並列に検索し（国土地理院の住所検索は区名がないと町名で引けないため）、町名と丁目（番地）の数字まで一致する結果を優先する（別の区にある「〇〇町西」のような、町名が前方一致するだけの結果より優先する）。自宅はブラウザ（localStorage）に保存
- **絞り込み**：区、クラス年齢（複数選択可）、施設種別、「空きがある施設のみ」、並び順（近い順／空きが多い順／名前順）
- スマホ幅では「リスト／地図」タブで切替

## データの更新

```bash
pnpm data:fetch    # 一次情報とマニフェストを取得
# マニフェスト差分と一次情報を確認
pnpm data:build    # 一次情報を検証し、PDFから抽出してsrc/data/facilities.jsonを再生成
# 生成結果を確認してPRを作成し、レビュー後に保管
pnpm data:archive
```

`data:update` は取得とビルドを続けて実行する便宜上のコマンドです。更新作業は取得 → 差分確認 → ビルド → PR → レビュー後に `data:archive` の順で進めます。取得直後に確認する場合は、上記のように `data:fetch` と `data:build` を分けて実行してください。

施設種別は `facilityType`、認可区分は `licensing` として別々に保持します。表示ラベルはアプリ側で定義します。

`src/schema.ts` の Valibot スキーマから公開データの型を導出し、生成時とアプリへの読み込み時に検証します。空き人数は0〜5歳の6件で、共有枠と各年齢の人数の整合、施設IDの一意性、区との対応、座標・URLなども確認します。定員内訳は未掲載なら空配列、掲載されていれば最大6件で合計が総定員と一致する形です。`scripts/data-schema.ts` は `data/<区>/*.json` と生成用の住所検索応答を検証します。

`pnpm test` はコミット済みの `src/data/facilities.json` を検証します。`pnpm check` と CI の `check` ジョブもこのテストを実行します。

対象の区と各区の取得元ページは `scripts/wards.ts` にまとまっています。区を追加するときはここに1件足し、`pnpm data:update` のあと `data/<区>/` に補完ファイル（下記）を用意します。

- `scripts/fetch-sources.ts [区のid]` … 市・区のページから CSV / xlsx / PDF / HTML を `sources/` に取得（区のidを渡すとその区だけ）
- `scripts/extract-pdf-details.ts` … 各施設の基本情報PDFから定員・開園時間などを位置ベースで抽出 → `data/<区>/pdf-details.json`（幼保連携型認定こども園の「1号」「2号・3号」に分かれた認可定員は合算し、内訳を注記）
- `scripts/extract-kigyo-details.ts` … 認可外保育施設一覧（詳細）PDFから企業主導型の開所時間・定員などを抽出 → `data/<区>/kigyo-details.json`（1ページ上下2施設の段組みを、区見出しの縦位置で施設ごとに分けて読む）
- `scripts/build-data.ts` … 上記と補完ファイルを突き合わせて `src/data/facilities.json` を生成（区の空き情報xlsxとCSVの自動照合、企業主導型の住所検索 → `data/<区>/geocode-cache.json` を含む）
- 補完ファイル（`data/<区>/`）：`manual-details.json`（自動抽出できない様式のPDFの目視転記）、`ward-details.json`（区資料からの補完・ふりがな補正・注記）、`websites.json`（公式サイトURL）
- `scripts/extract-ward-homepages.ts <区のid>` … 区の施設紹介資料PDFの「ホームページ」「URL」「ホームページアドレス」欄・区のページの「〇〇のホームページ」リンクや表の施設名リンク・施設の写真のリンクを一覧表示（`websites.json` 更新時の確認用）
- `scripts/check-urls.ts <区のid>` … `websites.json` のURLが開けるか確認（Cloudflare等で自動アクセスが拒否されるサイトはブラウザで確認）
- `scripts/dump-pdf-text.ts` … PDFのテキストを座標付きで表示するデバッグ用

### 一次情報を保管・復元する

非公開のR2バケットを用意し、そのバケットだけを対象とする **Object Read & Write** 権限のR2 APIトークンを発行してください。`.env.example` を `.env` にコピーし、`R2_ACCOUNT_ID`、`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、`R2_BUCKET` を設定します。`.env` はGitに含めません。各コマンドはファイルが存在するときだけNode.jsの `process.loadEnvFile('.env')` で読み込み、環境変数も使用できます。

```bash
pnpm data:archive                   # 全24区と全市共通を保管
pnpm data:archive chuo city         # 指定した単位だけ保管
pnpm data:restore                   # 作業ツリーのマニフェストの取得日で全単位をsources/へ復元
pnpm data:restore chuo@2026-10-21 --dest .audit/restored
pnpm data:manifest chuo --date 2026-10-21
```

`data:fetch` は区を指定した場合も全市共通の `city` を対象にします。`sources/city/` が存在し、作業ツリーのマニフェストの取得日がJSTの当日で、全ファイルのハッシュとサイズが一致するときだけ `city` の再取得を省略します。`pnpm data:fetch chuo --force-city` で再取得できます。

既存の `sources/<id>/` を `data:fetch` または `data:restore` で置換するときは、作業ツリーの `data/<id>/snapshot.json` が存在し、ディスク上の全ファイルがそのマニフェストと完全に一致し、R2認証情報が揃い、R2の `snapshots/<id>/<取得日>/snapshot.json` が同じSHA-256で保管されていることを確認します。`sources/` はブランチ・worktree間で共有されることがあるため、マニフェストの保管状況だけでは置換を許可しません。置換先がなければこの確認は不要です。fetchは `city` を含む対象すべてをダウンロード前に検査します。

条件を満たさない場合は、対象idと理由を表示して取得前に停止します。ツリーと作業ツリーのマニフェストが一致するブランチで `pnpm data:archive <id>` を実行してください。保管と保管状況の確認の両方に `.env` のR2認証情報が必要です。R2の確認中に通信障害が起きた場合は再試行してください。旧ツリーを削除してよい場合は、`pnpm data:fetch chuo --discard-unarchived chuo` または `pnpm data:restore chuo --discard-unarchived chuo` のように対象idを明示して再実行できます。この指定は選択したidごとに必要です。複数なら `--discard-unarchived chuo --discard-unarchived city` と繰り返します。fetchでは位置引数の区idも必須です。リンクや通常ファイルの置換は削除許可があっても拒否します。別ディレクトリへの `--dest` 復元は保管状況の確認をせず置換します（通常ファイルやリンクは取得前に拒否します）。`sources/` と実パスが同じ `--dest` は、Windowsの大文字小文字違いやjunction経由でも通常の `sources/` 復元として扱います。

取得した一式は `wards.ts` に応じた必須ファイルを確認してから置換します。旧一式は置換とマニフェスト更新が成功したあとで削除します。

Windowsで使用中のファイルによるrename失敗は、合計約9秒を上限に再試行します。取得・検証・置換・マニフェスト更新に失敗した場合は旧一式を保持または復元し、ダウンロード用の一時ディレクトリを削除せず、そのパスをエラーに表示します。

一次情報は `sources/<区id>/` と `sources/city/` に置きます。`data/<id>/snapshot.json` は取得日・相対POSIXパス・SHA-256・バイト数を記録します。`data:manifest [<id> ...] [--date YYYY-MM-DD]` は既存ファイルからマニフェストを作成します。日付を省略すると、ファイルの更新日時をJSTに変換し、単位内ですべて同日であることを確認します。通常は取得コマンドがJSTの当日付で自動生成するため、手動生成は初回取り込みに使います。

`data:archive [<id> ...]` はローカル一式がマニフェストと完全に一致することを確認し、`snapshots/<id>/<取得日>/<相対パス>` と同階層の `snapshot.json` を保管します。まずR2の `snapshot.json` をHEADで確認します。同じSHA-256ならその単位全体を省略し、異なる場合はアップロード前に失敗します。マニフェストがない場合はファイルを保管し、最後にマニフェストを保管します。途中まで保管済みのファイルは同じSHA-256なら省略し、異なる内容は上書きせず失敗します。途中失敗した場合は同じコマンドを再実行してください。同じ取得日に内容が変わった場合も上書きできないため、新しい取得日のスナップショットとして取り込みます。

`data:restore [<id>[@YYYY-MM-DD] ...] [--dest <dir>]` は省略時に全単位・作業ツリーのマニフェストの取得日・`sources/` を選びます。作業ツリーのマニフェストの取得日を復元する場合は、R2のマニフェストの全ファイル情報が作業ツリーのマニフェストと一致することも確認します。ハッシュとサイズを確認した一式だけをディレクトリごと置換し、不要になった旧ファイルは残しません。ただし、削除許可なしで `sources/` を置換するときは退避した旧ツリーを削除前に再検証します。取得中に旧ツリーが変わった場合や再検証できない場合は、旧ツリーを元の場所に戻し、取得した一式の保存先を表示して失敗します。別日付を `sources/` に復元したときは、`data/<id>/snapshot.json` もその日付へ更新して通知します。別の `--dest` への復元では、作業ツリーのマニフェストを変更しません。

`data:verify [<id> ...]` は一次情報を作業ツリーのマニフェストと照合します。`data:build` はすべての単位の検証を抽出処理より先に実行します。マニフェストや一次情報の欠落・不一致がある場合は、`data/` に書き込む前に停止し、`data:restore` を案内します。`facilities.json` の各区の `snapshot` と全市共通の `citySnapshot` に、使用した取得日を記録します。保管は [ADR 0001](docs/adr/0001-raw-sources-in-r2-per-ward-snapshots.md) に従いレビュー後に実行し、取得時にはアップロードしません。


## 地図タイルを作る・保管する

Protomapsの日次ビルドから、大阪市の範囲 `[135.36, 34.56, 135.62, 34.77]`（西・南・東・北）にかかるz0〜15のタイルを切り出します。範囲とズームは `scripts/map-tiles/config.ts` で定義します。Worker は `data/map/tiles.json` の build と保管先を使い、gzip の MVT を配信します。画面は MapLibre GL JS と react-map-gl/maplibre で表示し、@protomaps/basemaps の light スタイルを日本語で使います。元タイルの最大ズーム15を超える部分は、18まで拡大して描画します。

地図専用の非公開R2バケットを作ります。`<name>` を作成するバケット名に置き換えてください。

```bash
pnpm exec wrangler r2 bucket create <name> --location apac
```

[R2 APIトークンの作成手順](https://developers.cloudflare.com/r2/api/tokens/)に従い、そのバケットだけを対象にした **Object Read & Write** のトークンを発行します。一次情報用のバケット・トークンとは分けます。`.env.example` を参考に、`.env` に次の変数を設定してください。`R2_ACCOUNT_ID` は一次情報用と共通です。

```dotenv
R2_ACCOUNT_ID=
R2_MAP_ACCESS_KEY_ID=
R2_MAP_SECRET_ACCESS_KEY=
R2_MAP_BUCKET=
```

切り出しにはR2の認証情報は不要です。保管コマンドは `.env` があれば読み込み、環境変数も使用できます。`.env` はGitに含めません。

```bash
pnpm map:extract --build 20261027
# data/map/tiles.jsonの差分を確認してPRを作成
# レビュー後に実行
pnpm map:archive
```

切り出しは `map-tiles/osaka-<build>.pmtiles` を作り、元ビルド・タイルの版・範囲・枚数・保管先のkey・SHA-256・バイト数を `data/map/tiles.json` に記録します。`build` は `YYYYMMDD` の8桁で指定します。`pnpm map:extract` でbuildを省くと、記録の `source.build` から作り直します。記録もなければ停止します。同じ入力からは同じSHA-256のファイルを生成します。20261027のビルドでは877枚、約46.5MBです。記録だけをコミットし、`map-tiles/` のファイルはGitに含めません。

ローカルでタイルを使うには、ファイルを用意して `pnpm map:local` を実行します。ファイルの SHA-256 とバイト数を確認してから、ローカル R2 の同じキーへ入れます。本番 R2 は変更しません。Vite と `wrangler dev --persist-to .wrangler/state` は同じ保存先を使います。E2E は専用の `.wrangler/e2e-state` に小さな検証用 PMTiles を入れます。

タイル配信の確認には、E2E と同じ Wrangler の経路を使います。

```bash
pnpm build
pnpm exec wrangler dev --config wrangler.jsonc --assets dist/client --local --persist-to .wrangler/state
```

`@cloudflare/vite-plugin` 1.64.0 と 1.65.0 の開発経路では、gzip 応答を展開した本文と圧縮時の Content-Length が混在し、タイルの取得が失敗します。`pnpm dev` は同じローカル R2 を読みますが、タイルの確認には上のコマンドを使ってください。

`map:archive` はローカルファイルのSHA-256とバイト数を記録と照合し、`tiles/osaka-<build>.pmtiles` に保管します。同じSHA-256で保管済みなら省略し、異なれば上書きせず停止します。新規のPUTには `If-None-Match: *` とSHA-256のメタデータを付け、保管後もHEADで確認します。通信障害や途中失敗のあとには同じコマンドを再実行できます。

タイルの出典は [Protomaps Basemap](https://docs.protomaps.com/basemaps/downloads) と [OpenStreetMap contributors](https://www.openstreetmap.org/copyright) です。OpenStreetMapのデータは [Open Database License（ODbL）](https://opendatacommons.org/licenses/odbl/) に従います。切り出したPMTilesにも元の出典メタデータを残します。地図を表示する際にはOpenStreetMapの出典を表示します。

フォントとアイコン画像は [basemaps-assets](https://github.com/protomaps/basemaps-assets/tree/028c18f713baecad011301ff7a69acc39bcc2ae7) の固定コミットから取得し、Worker の静的アセットとして同じオリジンから配信します。取得し直すときは `pnpm map:assets` を実行してください。`data/map/assets.json` にコミット、fontstack、範囲、ファイルごとのバイト数とSHA-256を記録しています。必要な範囲は `pnpm map:glyphs` でローカルの実PMTilesの全ラベルを走査し、`data/map/glyph-coverage.json` にfontstackごとに記録します。タイルを更新するときは走査後に `pnpm map:assets` を実行してください。基礎ラテン文字と一般句読点に加え、記録した範囲を配信します。上流にない補助異体字セレクタの範囲は空のfontstackを持つPBFを生成し、基底文字を表示します。日本語の文字は `localIdeographFontFamily: 'sans-serif'` で端末のフォントを使います。

Noto Sans の glyphs は [SIL Open Font License 1.1](public/map/assets/fonts/OFL.txt)、v4 light の sprite は [MIT License](https://github.com/tangrams/icons/blob/master/LICENSE.md) に従います。sprite は1xと2xを同梱します。MapLibre 6 のESM workerをViteのアセットとして出力し、`setWorkerUrl` で指定するため、CSPの `worker-src 'self'` で動作します。
